# Forecast Layer Integration (Smoke Pass) — Design

**Date:** 2026-07-22
**Status:** Approved

## Purpose

`project_design.md`'s platform provides data; it says nothing about prediction. This spec
covers the first slice of a "prediction layer" on top of `market_data_schema.sql`: wiring
`AIML-ML-Multi-Forecast-Engine` — an existing, independently-hosted, dataset-agnostic
multi-series forecasting engine (Azure DevOps repo, `../AIML-ML-Multi-Forecast-Engine`
relative to this repo, branch `develop`) — to forecast every asset in `market_data`
uniformly, without modifying the engine itself.

The engine expects one homogeneous `(target, date, keys)` table per run. `market_data`'s
domain tables don't share a shape (`fx_rates.rate`, `commodity_futures.close`,
`bars_ohlcv.close`), so this spec adds a small unifying view and a forecast config that
targets it — validated with a synthetic sample, since `market_data`'s tables have no rows
yet (schema-only, per `docs/superpowers/specs/2026-07-22-market-data-schema-design.md`).

## Requirements

- A new BigQuery view, `market_data.forecast_assets`, projecting every daily, price-like
  asset in `market_data` onto one shape: `(catalog_id, date, value, domain_table)`.
- A forecast config (YAML) in `macro_data`, under a new `forecasting/` directory, mapping
  that view onto the engine's `dataset` contract: `target: value`, `date: date`,
  `freq: "D"`, and the engine's fixed two-level grain (`keys.item` / `keys.location`) filled
  with `catalog_id` / `domain_table` respectively (see "Grain mapping" below).
- A synthetic sample dataset (local, generated by a small script) shaped exactly like
  `forecast_assets`'s output, used to smoke-test the config end to end without live
  BigQuery data.
- The config must be runnable with `uv run horizons run --mode smoke --config <path>` from
  inside `AIML-ML-Multi-Forecast-Engine`, with `<path>` pointing at the config file living in
  `macro_data` — no file needs to be copied into the engine's own `configs/` directory.
- `AIML-ML-Multi-Forecast-Engine` itself is not modified — this is its documented,
  zero-src-change extension point ("Adding a new dataset = new config file").

### Grain mapping

The engine's `DatasetConfig.keys` (`GrainKeys` in `pipelines/demand_forecast/src/config/schema.py`)
is a fixed two-slot model — `item` and `location`, both required (with defaults
`item_id`/`store_id`), not a free-form list. Every shipped example config uses a true
item×location pair (e.g. `item_id` × `store_id`, one item sold at many stores).

`market_data`'s assets have only one natural identifier, `catalog_id`. This spec maps
`keys.item: catalog_id` and `keys.location: domain_table` (`fx_rates` / `commodity_futures`
/ `bars_ohlcv`). This satisfies the schema, but it's a **degenerate** fit: each `catalog_id`
has exactly one `domain_table` value, so `location` never varies independently of `item` the
way `store_id` does for a given `item_id` in the engine's intended use case. The pipeline
should still run correctly (nothing in the CV/feature/leakage logic requires location to
vary per item), but any hierarchical or cross-location features would be no-ops here — an
accepted limitation for this pass, not a defect to fix.

## Non-goals

- No real data ingestion into `market_data` — the view will return zero rows until a
  separate future ingestion pipeline exists (tracked in
  [[market-data-platform-schema]] memory / `project_design.md` §9). This pass validates the
  *mapping*, not real forecasts.
- No production run, no BigQuery write-back of predictions, no hyperparameter tuning
  (`tuning.enabled: false`), no SHAP/interpretability.
- No changes inside `AIML-ML-Multi-Forecast-Engine` (its own repo, own review process).
- No economic indicators, weather, or holidays — those aren't daily price series and don't
  fit one `freq: "D"` config (the engine is frequency-agnostic per-run, not mixed-frequency
  within a run). A monthly/quarterly indicators config is a separate future spec.
- `ticks` is excluded (streaming, not daily-aggregated; no natural single daily value).

## Architecture

### 1. The view — `forecasting/market_data_forecast_view.sql`

A new, separate file (not appended to `market_data_schema.sql`, which is scoped to the base
12-table schema) — kept in `macro_data`, alongside the config that consumes it:

```sql
-- forecast_assets: unifies every daily, price-like asset in market_data onto one shape
-- for AIML-ML-Multi-Forecast-Engine. See docs/superpowers/specs/2026-07-22-forecast-layer-integration-design.md.
--
-- Replace `your-gcp-project` with your actual GCP project id, matching market_data_schema.sql.

CREATE VIEW `your-gcp-project.market_data.forecast_assets` AS

SELECT
  catalog_id,
  rate_date AS date,
  rate AS value,
  'fx_rates' AS domain_table
FROM `your-gcp-project.market_data.fx_rates`

UNION ALL

SELECT
  catalog_id,
  trade_date AS date,
  close AS value,
  'commodity_futures' AS domain_table
FROM `your-gcp-project.market_data.commodity_futures`

UNION ALL

SELECT
  s.catalog_id,
  DATE(b.bar_start_ts) AS date,
  b.close AS value,
  'bars_ohlcv' AS domain_table
FROM `your-gcp-project.market_data.bars_ohlcv` AS b
INNER JOIN `your-gcp-project.market_data.symbols` AS s
  ON b.symbol_id = s.symbol_id
WHERE b.`interval` = 'daily';
```

`bars_ohlcv` has no `catalog_id` column directly (only `symbol_id`) — it requires the join
through `symbols` to reach `catalog_id`, unlike `fx_rates`/`commodity_futures` which carry
`catalog_id` natively. The `WHERE interval = 'daily'` filter picks one bar resolution per
symbol so each `(catalog_id, date)` pair is unique — `'daily'` is a convention this spec
introduces (not enforced by `market_data_schema.sql`, which leaves `interval` as a free
`STRING`); any future ingestion into `bars_ohlcv` must use this literal for daily bars for
the view to pick them up.

### 2. Synthetic sample generator — `forecasting/generate_synthetic_sample.py`

A standalone script (pure pandas/numpy, no BigQuery dependency) producing a local Parquet
file shaped exactly like `forecast_assets`'s output:

```python
def generate_synthetic_assets(
    n_assets_per_domain: int = 5,
    start: str = "2023-01-01",
    end: str = "2026-07-22",
    seed: int = 42,
) -> pd.DataFrame:
    """Returns a DataFrame with columns (catalog_id, date, value, domain_table) --
    one random-walk price series per synthetic asset, for smoke-testing the forecast
    config's dataset/keys mapping without live BigQuery data."""
```

- 3 domains × `n_assets_per_domain` = 15 synthetic assets by default, ~3.5 years of daily
  history each (comfortably above the `runway_days`/`window_size_days` needed for the
  horizons below).
- Each series is a geometric random walk seeded off a domain-specific base price (FX ~
  1.0-40.0, commodities ~ 20-2000, equity bars ~ 50-5000) so magnitudes look plausible
  without claiming to be real data.
- Written to `forecasting/data/synthetic_forecast_assets.parquet`.

### 3. The config — `forecasting/configs/market_data_assets_smoke.yaml`

Modeled directly on the engine's own `m5_demo_quickstart.yaml` (parquet, committed sample
data, `mode: experiment` + `smoke:` overrides — the pattern the engine's README recommends
for a first end-to-end validation):

```yaml
mode: experiment

experiment_name: market_data_assets_smoke
artifacts_dir: artifacts/market_data_assets_smoke

dataset:
  target: value
  date: date
  freq: "D"
  keys:
    item: catalog_id
    location: domain_table

data_sources:
  modeling_base:
    type: parquet
    # Relative to the CLI's cwd at invocation time (the engine resolves
    # data_sources paths relative to cwd, not to the config file's own
    # location -- see "Running it" below), not relative to this file.
    path: ../Macro_data/forecasting/data/synthetic_forecast_assets.parquet

preprocessing:
  densify_grid: true
  detrend:
    mode: normal
    window: 28
  normalize:
    enabled: false
  postprocessing:
    clip_negative: true
    round_to_integer: false

features:
  calendar:
    enabled: true
  events:
    enabled: false
  hierarchical:
    enabled: false
  matrix_features:
    enabled: true
    lags:
      target: [1, 7, 14, 30]
    rolling_means: [7, 30]
    ewma_alphas: [0.1]
  cyclical:
    enabled: false
  volatility:
    enabled: false
  external: []

horizon:
  horizons: [1, 7, 30]
  unit: days
  architectures: [direct]

validation:
  strategy: expanding_window
  n_folds: 1
  window_size_days: 90
  test_days: 30
  runway_days: 30

tuning:
  enabled: false

models:
  selection_metric: mae
  lightgbm:
    enabled: true
    num_boost_round: 50
    early_stopping_rounds: 10
    base_params:
      boosting_type: gbdt
      learning_rate: 0.05
      random_state: 42
      verbose: -1
      n_jobs: -1
      feature_pre_filter: false
    variants:
      - name: lgb_l1
  xgboost:
    enabled: false
  baseline:
    enabled: false

output:
  predictions:
    type: parquet
    path: artifacts/market_data_assets_smoke/predictions.parquet

interpretability:
  shap:
    enabled: false

memory:
  budget_gb: 8.0
  warn_at_fraction: 0.75
  abort_at_fraction: 0.90
  warn_only: true

cache:
  enabled: false
  post_horizon_path: null
  overwrite: false

smoke:
  sample_n_series: 15
  n_folds: 1
  n_trials: 1
  horizons: [1, 7, 30]
  architectures: [direct]
```

`runway_days: 30` matches the max horizon (30) per the engine's own leakage rule
(`runway_days` must be ≥ max horizon in calendar days, enforced by its
`runway_covers_horizon` validator) — this is a hard requirement, not a tuning choice.

The **real** BigQuery-backed variant of this config (pointing `data_sources.modeling_base`
at `type: bigquery`, `table: forecast_assets`) is written but not run in this pass — it's
included in `forecasting/configs/market_data_assets_bigquery.yaml` as a documented next
step for once `market_data` has real rows, per the Non-goals above.

### 4. Running it

Documented in `forecasting/README.md`, not wrapped in new orchestration code (the engine's
own CLI is the interface):

```bash
cd AIML-ML-Multi-Forecast-Engine
uv run horizons run --mode smoke --config ../Macro_data/forecasting/configs/market_data_assets_smoke.yaml
```

The `--config` argument itself can be any path (absolute or relative to cwd) — the engine
doesn't require configs to live inside its own `configs/` directory. But every path
*inside* the config (`data_sources.modeling_base.path`, `output.predictions.path`,
`artifacts_dir`) is resolved relative to the CLI's cwd at invocation time, which is why the
sample data path above is `../Macro_data/...` rather than `forecasting/...`. Output
artifacts (`artifacts/market_data_assets_smoke/`) are therefore written inside
`AIML-ML-Multi-Forecast-Engine/`, not `macro_data/` — consistent with every other example
config in that repo, and left as-is (not redirected into `macro_data`) since these are
engine-side run artifacts, not a `macro_data` deliverable. The README documents an absolute
`--config` path as an alternative if the two repos aren't checked out side by side.

## Testing

- `forecasting/generate_synthetic_sample.py`'s `generate_synthetic_assets()` is a pure
  function — covered by a unit test in `macro_data`'s existing `tests/` (asserts column
  names/dtypes, no nulls in `value`, exactly `3 * n_assets_per_domain` distinct
  `catalog_id`s, all three `domain_table` values present).
- The config itself and the view SQL are validated by actually running
  `uv run horizons run --mode smoke --config ...` against the generated synthetic parquet
  and confirming it completes without error and writes
  `artifacts/market_data_assets_smoke/predictions.parquet` — this is an integration check
  run manually during implementation (see plan), not part of `macro_data`'s `pytest` suite,
  since it depends on a sibling repo/environment outside this one.
- The view SQL itself cannot be executed against real BigQuery in this environment (no
  `GCP_PROJECT` configured) — reviewed by hand, same as `market_data_schema.sql`.

## Out of scope

- Real ingestion into `market_data` (separate future spec).
- The BigQuery-backed config variant actually being run (written for later use only).
- Production mode, champion promotion, predictions written back to BigQuery.
- Any change inside `AIML-ML-Multi-Forecast-Engine`.
- Economic indicators / weather / holidays forecasting (different frequency, separate spec).
